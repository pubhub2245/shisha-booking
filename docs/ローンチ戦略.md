## 0. この文書の目的
この文書は、Claude Code / Claude のメモリーへ渡すための「煙道 ENDO」のローンチ戦略・初期運用方針の引き継ぎ資料。

現在の煙道は、機能不足よりも「初期データ不足」「初期作り手不足」「実体験データ不足」が最大のボトルネック。
ここからは機能開発を増やすより、実ユーザー・作り手・店舗・method・experience を増やし、プロダクトの本当の価値を検証するフェーズへ移る。

---

# 1. 現在のプロダクトコンセプト

## ブランド
**煙道 ENDO**

## ミッション
**日本のシーシャの「王道」を、みんなでつくる。**

## コアループ
**探す → 作る → 吸う → 残す → 深める**

## 基本思想
- combo = フレーバーの組み合わせ
- method = 具体的な一台の作り方
- experience = 実際に「吸った / 作った」体験
- 王道 = 同一combo内で公式に認定されたmethod
- 推薦 = 認証プロ / 運営によるmethod推薦
- taste = 実際に吸った人による味覚5軸
- 初心者には「まずこれ」
- 上級者には器具・熱管理・味覚等を段階開示
- 「初心者モード / プロモード」の完全分離はしない

---

# 2. 現在のフェーズ判断

現時点では、大きな新機能追加を止める。

次の最大リスクは「機能不足」ではなく、

**誰もいないこと / データが薄いこと**

である。

特に現状は、
- method数が少ない
- 王道が少ない / 0件になりやすい
- tasteデータが少ない
- experienceデータが少ない
- 店舗データが少ない

ため、今後は「開発」より「初期流通量」を増やす。

---

# 3. ローンチの3フェーズ

## Phase 0 — 公開前
目的：
**空のプラットフォームにしない**

目標：
- 100〜150 method
- 10〜20人の作り手
- 5〜10店舗
- 10〜20個の主要combo
- 3〜5件の公式王道

一般公開前に「検索すれば何か出る」状態を作る。

## Phase 1 — 初月
目的：
**検索されることより、実際に吸われて記録されることを優先**

目標の目安：
- 300 method
- 月間「吸った」500件
- made 100件
- taste evaluation 150件
- 公式王道 10〜20件
- active creator 20人程度

最重要KPI：
**月間 smoke experience 数**

## Phase 2 — 2〜3か月目
目的：
**人と店舗のネットワークを作る**

目標の目安：
- 作り手 50人
- 店舗 20〜30店
- 月間「吸った」2,000件
- 公式王道 30件以上
- 「この王道を吸える店舗」などの店舗連携を開始

# 4. ローンチ時のmethod数

一般公開時点では **150前後** を目安にする。
300件まで待つ必要はない。

目安の内訳：
- フルーツ系：40
- 爽快・ミント系：25
- シトラス系：20
- ベリー系：15
- デザート系：15
- ドリンク系：10
- スパイス・ハーブ系：10
- ダブルアップル系：10
- その他：5

重要なのは「数」より、
**主要な検索をした時に空にならないこと。**

---

# 5. methodの品質配分

150 method 全部をプロ品質にしなくてよい。

推奨：
- 約100件：かんたん投稿レベル
  - フレーバー
  - 配合
  - 一言
- 約50件：詳細method
  - ボウル
  - HMD
  - 炭
  - 蒸らし
  - 熱管理
  - 詳細ノウハウ

公開後に詳細が育つ構造を許容する。

---

# 6. 初期methodの集め方

3経路で集める。

## A. 運営投入
まず50 method程度。
目的：検索した時の「空」を防ぐ。

投稿者は一般UGCに見せかけず、
**「煙道編集部」**
として明示する。

## B. 創設作り手
10人 × 5〜10method
→ 50〜100method

有名人より、
**実際に投稿してくれる人**
を優先する。

優先条件：
- 店舗スタッフ
- 店長
- オーナー
- 自宅シーシャ玄人
- シーシャ発信者
- 作り方を言語化できる
- 5〜10methodを出せる

フォロワー数より「データ貢献量」を重視。

## C. 一般投稿
公開後に自然増。
一般ユーザーへ最初から詳細投稿を要求しない。

---

# 7. 創設メンバー制度

最初の30人程度を、
**煙道 創設作り手**
として扱う案。

メリット例：
- プロフィールに創設表示
- 先行投稿
- フィードバック会
- 将来の紹介・特集で優先

過剰なゲーミフィケーション・金銭報酬はまだ不要。
参加理由は、
**「日本のシーシャの基準を作る初期メンバー」**
という意味付けを中心にする。

---

# 8. 初期店舗

最初は全国100店舗を狙わない。
**本当に協力してくれる5〜10店舗**で十分。

目安：
- 東京 2〜3
- 大阪 1〜2
- 福岡 1
- 宮崎 1
- その他 2〜3

店舗には在庫登録だけでなく、
**その店舗の作り手が投稿したmethod**
を持たせる。

「店舗情報」ではなく「味 / 作り手」と結びつける。

---

# 9. 最初の公式王道

王道0件のまま一般公開するより、少数でも公式王道がある方が良い。
初期目標：**3〜5件**

候補例：
- ダブルアップル × ミント
- マンゴー × 清涼系
- レモン × ミント
- ベリー × ミント
- デザート系代表

王道を乱発しない。
「王道」のブランド価値を守る。

---

# 10. 初期王道の認定運用

初期は完全アルゴリズム化しない。

王道候補の目安：
- 同一comboに2method以上
- 合計experience 10件以上
- made 3件以上
- 極端な低評価が少ない
- 運営確認

その上で、
**「現時点でまずこれ」**
として公式認定。

王道は永久固定ではなく、後から更新可能。

---

# 11. 一般ユーザーに最初にお願いする行動

最初から全部お願いしない。

NG：
- 投稿して
- コメントして
- 味覚5軸も入力して
- 作って
- 評価して

最初の主CTAは1つ。

**「吸ったら『吸った』を押してください。」**

その後は任意で、
- verdict
- taste
- made
へ進む。

# 12. KPI

## North Star Metric
**月間「吸った」登録数**

定義：
experience_type IN ('smoked','made')

## 補助KPI
- made数
- taste evaluation数
- 保存数
- 新規method数
- active creator数
- 王道数

## ファネル
mix詳細閲覧
→ 保存
→ 吸った
→ verdict
→ taste
→ made

重要：PVや登録者数だけで成功判断しない。

# 13. 初期ユーザー獲得

優先順位：
1. 作り手本人のSNS
2. 協力店舗の来店客
3. シーシャ関連X / Instagram
4. 店舗QR
5. 口コミ

広告は後回し。
理由：データが薄い状態で大量流入させても離脱するだけ。

---

# 14. 店舗QR

Phase 1から、
**「この一台を煙道で見る」QR**
を店舗・メニュー・テーブル等に置く案。

導線：
QR
→ method詳細
→ 吸った
→ verdict
→ taste（任意）

最初から厳格なVerified Smokeにしなくてよい。
店舗経由流入を記録できるだけでも価値がある。

---

# 15. 初期コンテンツで絶対に避けること

- 150method全部が同じ運営アカウント
- 全methodがほぼ同じ文章
- 王道を大量認定
- 味覚データを架空投入
- 「吸った」experienceを運営が水増し
- 店舗0件で店舗ランキングを前面表示
- 架空のユーザー実績を作る

特にexperience / tasteは**絶対に架空で水増ししない**。
煙道の将来価値は信頼できる実体験データなので、初期からデータを汚さない。

# 20. 事業側の短い言語化

## 一言
**日本のシーシャの「王道」を、みんなでつくる。**

## ユーザー体験
**迷ったら、まず王道。**
**吸ったら、残す。**
**作り手は、次の一台を残す。**

実際に吸われ、再現されながら、日本のシーシャの基準が育っていく。

---

# 21. Claude / Claude Code への行動原則

1. 新機能追加より、実ユーザー・実データを増やす
2. 迷ったら「吸った」体験を最優先
3. 王道を人気投票化しない
4. 架空experience / tasteを作らない
5. 初心者に情報を見せすぎない
6. 上級者には段階開示で深い情報を提供
7. 既存コアループを壊さない
8. 機能を増やす前に、削る・並べ替える・言い換える
9. production確認までを「実装完了」と定義する
10. 実データが無いと判断できない問題は、机上で作り込みすぎない

## 最重要メモ

現在の煙道は、
**「もっと機能を作る段階」ではなく、「人とデータを入れて本当に回るかを検証する段階」**。

次の最大リスクはコードではない。

**初期流通量・作り手・experience・taste・王道が足りないこと。**

開発より、ここを優先する。
