## 1. まず、なぜ人は他人の METHOD を試さないのか

仕組みを設計する前に、障壁を具体的に特定する。シーシャ固有の事情が大きい。

| # | 障壁 | 深刻度 | 実装で効くか |
|---|---|---|---|
| 1 | **1台 2.5時間＋タバコ代**。失敗したときの損失が大きく、冒険しにくい | 最大 | 部分的（外れを引かせない提示） |
| 2 | **器材が違って物理的に再現できない**（ボウル・HMD・炭が無い） | 大 | ○ 実行可能なものだけ見せる |
| 3 | **どれを試せばいいか分からない**（選択肢が並ぶだけでは選べない） | 大 | ◎ 1件を名指しで提示 |
| 4 | **自分のやり方と何が違うのか分からない＝試す理由がない** | 最大 | ◎ 差分を言語化する |

**4 が本質。** 「おすすめの作り方」は動機にならないが、
**「これはあなたのやり方と『炭の数』だけが違います」** は動機になる。
知的好奇心が具体的な差分に接続された瞬間に、2.5時間を払う理由が生まれる。

**そして 2 は現状のDBでは扱えない**（後述 §5 で判明。`shelf` はフレーバー所有のみで器材を持たない）。

## 2. 「他人の METHOD を試したくなる仕組み」＝ 4つの部品

### M1. 基準点をつくる（Baseline）

**テーマ参加の第一歩を「自分のいつものやり方に一番近い METHOD を1つ作る」にする。**

参加者は2種類に分け、**既定は投稿しない側**にする。

| | 入口 | 1台目 |
|---|---|---|
| **検証者**（既定・多数） | 投稿しない | 検証対象 METHOD から「自分のやり方に一番近いもの」を選んで作る |
| **作り手**（少数） | 自分の METHOD を投稿 | 自分の METHOD を作る（＝Original） |

これにより、
- 新規参加のハードルが「投稿」ではなく「いつも通り作る」になる
- **1台目が自動的に比較の基準点になる**
- Primary KPI「2METHOD以上」の**1つ目を、通常の行動だけで獲得できる**

> **重要**：全員に投稿させない。参加者50人が全員自分の METHOD を投稿すると
> 50 method に再現が分散し（80再現 ÷ 50 = 1.6/method）、**どの method も検証に届かない**。
> 後述 M3 の「検証対象枠」と合わせて、投稿より**検証**を既定にする。

### M2. 差分を名指しする（Diff）

2台目以降に提示するのは「おすすめ」ではなく **「あなたの1台目と、ここが違う METHOD」**。

```
あなたが作った #03 と比べて

  炭の数     3個 → 2個
  初期加熱   5分 → 8分

  ボウル・詰め方・HMD は同じ

この違いで、味がどう変わるか試してみませんか？
```

**選定ルール（実験設計として重要）**
- **最大限に違うものを選ばない。**「1〜2軸だけ違う」ものを選ぶ
  - 多変数が同時に変わると、差の原因が分からず**学びが発生しない**
  - 心理的にも「全部違う」は遠く、「炭の数だけ違う」は近い
- 同点なら**再現数が少ない METHOD** を優先（データの穴を埋める）
- 既に作った METHOD は除外

### M3. 実行可能なものだけを見せる（Feasibility）

器材が無い METHOD を提示すると、その場で離脱する。
→ 参加時に一度だけ「持っている器材」を登録してもらい、実行できないものは推薦から外す。
（現状のDBには器材所有の概念がない。§5 で扱う）

**さらに「検証対象 METHOD」という限定枠を設ける。**

- 誰でもテーマに投稿できる（自由投稿は閉じない）
- ただし**検証の対象として推薦されるのは、運営が指定した 8〜12 件のみ**
- 理由は集中：再現80件が10 methodに集まれば平均8件で判定材料になるが、
  50 methodに散れば平均1.6件で**何も言えない**

これは制限ではなく**実験の設計**。テーブル追加は不要（運営が combo 内の method を指定するだけ）。

### M4. 記録した直後に「発見」を返す（Feedback）★最重要

現在は「作った」を押しても件数が増えるだけで、**ユーザーには何も返らない**。
（`components/made-button.tsx` は楽観更新でカウントを+1するのみ。実測で確認済み）

記録直後に返すもの、優先順位順：

```
① あなたの中の比較 ★煙道にしかない
   あなたの1台目（#03）と比べて
     甘さ    3 → 4   （+1）
     重さ    4 → 3   （−1）
   → 炭を1個減らすと、あなたには軽く・甘く感じられた

② 全体の中での位置
   あなたは #07 の 12人目の再現者です
   この METHOD の平均：甘さ 4.0 / 重さ 3.2（評価者5人）
   ※評価者3人未満のときは平均を出さない（既存の MIN_RATERS_FOR_AVERAGE = 3 に従う）

③ 次の一歩
   まだ試していない検証対象：4件
   次に試すと面白いのは #11（あなたの #07 と「詰め方」だけが違います）
```

**①が生命線。** ②は他サービスでも作れるが、①は
「同じ人が複数 METHOD を作る」構造を持つ煙道にしか出せない。
そして①が出ることが、**2台目を作る最大の報酬**になる。

> ①は1台目には出せない（比較対象がないため）。
> 1台目の記録後は「**次にもう1つ作ると、あなたの中での比較が出ます**」と予告する。
> これが2台目への最も強い動線になる。

## 3. ユーザージャーニー（一本のフロー）

```
─────────────────────────────────────────────────
[0] 流入
    X / 知人 / 店舗の卓上QR / 検索
      ↓
[1] トップ（通常の煙道。図鑑・検索・保存がある）
    その中に1枚だけ特別エリア：
    ┌──────────────────────────┐
    │  今月の煙道検証                        │
    │  AL FAKHER  ダブルアップル             │
    │  この一台の、最適解を探す。            │
    │  検証対象 10 ／ 作った人 32 ／ 比較中 14 │
    └──────────────────────────┘
      ↓
[2] テーマページ（＝既存の /combo/[slug] を拡張）
    ・問い（何を検証しているか、なぜ100%なのか）
    ・熱カーブ比較（実装済み。ここで初めて意味を持つ）
    ・★主導線：「まず、あなたのいつものやり方に近い1台を作る」
       → 器材で絞った検証対象を3件だけ提示（多く見せない）
      ↓
[3] METHOD を1つ選ぶ（/mix/[id]）
    ・作り方（ボウル/詰め方/HMD/炭/初期加熱/熱管理）
    ・作り手の実績（author_endo_stats・実装済み）
    ・何人が再現したか
      ↓
[4] 実際に作る（2.5時間）
      ↓
[5] 記録する ★吸い終わった後のタイミング
    「作った」1タップ → どうだった？4択 → 味の印象5軸（任意）
    （すべて実装済み）
      ↓
[6] ★発見を返す（現在存在しない）
    1台目 → 「あなたは12人目の再現者」＋「もう1つ作ると比較が出ます」
    2台目〜→ ①あなたの中の比較 ②全体の中での位置 ③次の1件
      ↓
[7] 次の METHOD へ（[3] に戻る。同じフレーバー・違うやり方）
    ここでユーザーが感じるのは「同じものを繰り返している」ではなく
    「別の人の思想を試している」
      ↓
[8] 2つ以上作った人 ＝ 比較参加者（Primary KPI）
    「自分はこっちが好きだった」を語れる状態になる
      ↓
[9] 蓄積 → 王道候補 → 煙道が確認 → 王道認定（combo_orthodoxy）
    ※8週の必達目標にはしない。自然発生したら「強い成功」
─────────────────────────────────────────────────
```

### 見せる言葉と、運営の目的を分ける

| 運営の目的（内部） | ユーザーに見せる言葉（外部） |
|---|---|
| 同一条件で反復検証する | **次はこの作り方を試してみよう** |
| 再現データを蓄積する | あなたの1台目と、ここが違います |
| 被験者内比較でノイズを消す | **あなたの中では、こっちの方が甘かった** |
| 王道を認定する | この一台の、最適解を探す |

**「同じものを擦る」は一度もユーザーに言わない。**

## 4. 入力項目の逆算（増やさない）

差分（M2）として**名指しできる軸だけ**が、入力する価値のある項目。
逆に、差分として言語化できない項目は、いま増やしても比較に寄与しない。

DA 100% で「他人が実行できて、差が名指しでき、味が変わりうる」軸は5つ。

| 軸 | 既存カラム | 既存フォーム | 差分表現の例 |
|---|---|---|---|
| ボウル | `bowl_type` | `BowlPicker`（実装済み） | ファンネル → キラー |
| 詰め方 | `pack_style` | `PackPicker`（実装済み） | ふんわり → みっちり |
| HMD | `hms_type` / `hms_other` | `HmsPicker`（実装済み） | HMD → 直火 |
| 炭の数 | `charcoal_count` | 数値入力（実装済み） | 3個 → 2個 |
| 初期加熱 | `steep_minutes` | 数値入力（実装済み） | 5分 → 8分 |

> **結論：第一テーマに必要な入力項目の追加は、ゼロ。**
> `mixes` には他にも `charcoal_orientation` `wind_cover` `heat_curve` `heat_events`
> `steep_heat` `base_liquid` `gear_*` などが既にあるが、**第一テーマでは差分軸に使わない**。
> 記録は任意のまま残し、比較の主軸は上の5つに絞る。

**検証対象 METHOD に選ぶ条件**：この5軸がすべて埋まっていること。
（一般投稿には要求しない。検証対象に指定するときの要件にする）

## 6. 指標の定義（査読の分類を採用）

### Primary（これ1つだけを主指標にする）

**複数METHOD参加者数**
= テーマ内で**2つ以上の異なる method** を `made` したユニークユーザー数

> 20人は「統計的に十分」ではなく、**「比較ループが回る規模に達した」**というプロダクトKPI。
> 20人到達＝王道が証明された、ではない。

### Secondary

METHOD数 ／ 作成回数 ／ リピート回数 ／ 評価数（taste） ／ 第三者比較数 ／ 店舗参加数

### コア接近度（煙道が煙道であるかを測る2指標）

| 指標 | 定義 | 読み方 |
|---|---|---|
| **他人METHOD実施率** | 他人の method を1つ以上作った人 ÷ 参加者 | 低い＝SNS化 |
| **1人あたりMETHOD横断数** | テーマ内 distinct method made の平均 | 1.1＝ほぼ投稿サイト／2.8＝比較サービス／3.5＝かなり良い |

とくに **METHOD投稿者のうち、他人の METHOD を1つ以上作った人の割合** を重視する。

```
投稿者100人 ／ 自分のMETHODしか作らない80人   → SNS化している
投稿者 40人 ／ 30人が他人のMETHODも作っている → 比較プラットフォームとして機能
```

**投稿者より検証者が増えることが健全。**

### Guardrail（悪化を検知する）

| 指標 | 定義 | 危険な状態 |
|---|---|---|
| 投稿だけして体験しない人の割合 | method 投稿者のうち experience 0件 の割合 | 高い＝見せたいだけの場 |
| 一度作って離脱する割合 | 参加者のうち distinct method = 1 で止まった割合 | 高い＝2台目の動機が無い（M4の失敗） |
| 同じMETHODに偏る割合 | 最多 method が全 reproduction に占める割合 | **高すぎても危険**（比較が成立しない） |

### 危険指標（査読で追加）

> **METHOD投稿者数 ＞ 2METHOD以上体験者数**

件数比較（method数 > experience数）より鋭い。
「経験を1回だけ登録した人100人 ／ 投稿者10人」は件数上は健全に見えるが、**深度がない**。
**ユニークユーザー単位**で見ることでこれを検出できる。

## 7. 8週間の判定（王道候補は必達にしない）

| 区分 | 条件 |
|---|---|
| **必達** | **比較参加者 20人**（2 METHOD 以上を作ったユニークユーザー） |
| 望ましい | 1人あたりMETHOD横断数 2.5 以上 ／ 他人METHOD実施率 60%以上 |
| **強い成功** | **王道候補が自然発生する**（期限を切って作るものではない） |
| 参考 | 参加者50人 ／ 検証対象10〜12件 ／ 再現70〜90件 ／ taste 3人以上ついた method 3件 |

### 王道候補が出なくても成立する成果

例：8週後に **参加者25人・2METHOD以上22人・平均2.8METHOD**、
しかし **METHOD間の評価差がほぼ無い**——という結果になった場合。

これは失敗ではなく、**「シーシャは作り方による差が思ったほど大きくない」という事業仮説の検証結果**である。
比較ループ自体は成立しているので、次に問うべきは「では何が味を決めるのか」になる。
（ただしこの結論は、差が無いことを示すデータが揃って初めて言える。早合点しない）

## 8. 撤退基準（3段階）

### 🔴 赤信号 — 投稿サイト化
- METHOD は増えるが、**他人の METHOD を作る人がほぼいない**
- 判定：`METHOD投稿者数 ＞ 2METHOD以上体験者数`、他人METHOD実施率 20%未満
- 対処：投稿導線を弱め、検証導線（M1〜M4）を作り直す。**METHOD を増やす施策は止める**

### 🟡 黄信号 — 比較体験が弱い
- 作る人はいるが、**1人1METHODで止まる**

## 9. combo_key 正準化 — 仕様のみ確定（実装は第一テーマ後）

### 現状（実測）

```ts
// lib/combo.ts
flavorKey = `${brand}|${name}`.toLowerCase()
comboKey  = [...unique].sort().join(' + ')
// 実際の値: 'al fakher|ダブルアップル'
//           'adalya|アイスアクア + al fakher|マンゴー'
```
`flavors` テーブルは `brand:text, name:text` のみで、**言語非依存の識別子を持たない**。
このままでは "Double Apple" と "ダブルアップル" が別 combo になり、世界共通の比較が成立しない。

### 確定する仕様（ルールのみ。今は実装しない）

> **combo の識別に表示名を使わない。Canonical Flavor ID を使う。**

```
flavors.canonical_id  text  unique  not null
  形式: <brand-slug>-<flavor-slug>
  文字種: 半角小文字英数字とハイフンのみ
  ブランド: 英語の正式表記をケバブケース化   AL FAKHER → al-fakher
  フレーバー: 英語の正式表記               ダブルアップル → double-apple
  同一物の別表記（Double Apple / ダブルアップル / DBA）は同一 canonical_id に集約する

combo_key = canonical_id を昇順ソートして ' + ' で連結
  例) 'al-fakher-double-apple'
      'adalya-ice-aqua + al-fakher-mango'

表示名は flavors.brand / flavors.name のまま（多言語表示は将来 flavors_i18n）
```

**移行手順（第一テーマ後に実行）**
1. `flavors` に `canonical_id` を付与（86件）
2. `mixes.combo_key` を再生成
3. `combo_orthodoxy.combo_key` を追随（`combo_orthodoxy_history` も）
4. 旧 slug の URL から 301

### なぜ今やらないか / なぜ今仕様だけ決めるか

現在 method 8 / combo 8 なので、移行コストはほぼゼロ。
**50〜100 method まで進んでから「日本語名と英語名が分裂している」と気づく方が、はるかに高くつく。**
一方で今すぐ移行しても第一テーマの成否には影響しない。
→ **仕様を確定して記録し、実装は第一テーマ後**。「とりあえず後で」にはしない。
