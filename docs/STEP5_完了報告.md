## 1. STEP 4 最終確認 2点の結果

### 0-1 今月集計のタイムゾーン → **バグを確認し修正しました**

実測でサーバーTZが **UTC** であることを確認（`TZ` 未設定 / `Intl` 解決結果が `UTC`）。
旧実装 `new Date(y, m, 1).toISOString()` は **`2026-08-01T00:00:00Z` = JST 08/01 09:00** を月初としていました。
つまり **日本時間 8/1 の 0:00〜9:00 の記録が前月扱い**になる、まさにご指摘の不具合です。

**修正**：`lib/time.ts` に `jstMonthStartIso()` を追加し、JSTの壁時計で月初を求めてUTCへ戻すようにしました（JSTは夏時間が無いので固定オフセットで安全）。

```ts
export function jstMonthStartIso(now: Date = new Date()): string {
  const jst = new Date(now.getTime() + JST_OFFSET_MS)
  const startUtcMs = Date.UTC(jst.getUTCFullYear(), jst.getUTCMonth(), 1) - JST_OFFSET_MS
  return new Date(startUtcMs).toISOString()
}
```

回帰テストを3件追加（いずれも合格）：
- JST月初 = `2026-07-31T15:00:00.000Z` を返す
- **JST 8/1 00:30 の記録が当月に含まれる**（旧実装での失敗ケース）
- JST 8/31 23:30 はまだ当月

> ユーザー別タイムゾーン対応は不要との方針どおり、`Asia/Tokyo` 固定です。

### 0-2 「N回目」の正確性 → **正確でした（変更なし）**

算出クエリは表示中ミックスに対して **ユーザーの全 experience を取得**しています（`limit` を付けていないため、そのmixの通算件数が対象）：

```ts
supabase.from('mix_experiences').select('id, mix_id, occurred_at')
  .eq('user_id', user.id).in('mix_id', mixIds)
```

タイムライン側の `limit(40)` は**表示する行数**にしか効かず、回数算出には影響しません。よって「3回目」は当該ミックスの通算体験数として正しい値です。
唯一の理論上の上限は PostgREST の既定最大行数（1000）で、1ユーザーが表示中ミックスに対して1000件を超える体験を持つ極端なケースのみ。V1では実害が無いため表示は維持しました（残課題に記載）。

## 6. % / g の扱い（**要ご判断の事項を含みます**）

**調査結果：現状の `mix_flavors.ratio` は「グラム」として扱われています。**
ミックス詳細は `{f.ratio}g` と表示し、`simple-mix-form` のプレースホルダも「量(g)」でした。

**今回の対応（非破壊）**：
- **列は増やさず、`ratio` 1本のまま**にしました。→ **二重入力が構造的に発生しないため矛盾が起きません**（「60%なのに3g/7g」という状態を作れない）。
- 表示は **合計を100として正規化した%** を用いるようにしました。%は尺度に依存しないため、**比率入力(40/60)でもグラム入力(3g/7g)でも正しく** `40 : 60` / `30 : 70` になります（実DBで確認済み）。
- かんたん投稿の入力欄は「配合」とし、比率でもグラムでも受け付ける旨を明記。

**⚠️ 残っている不整合（未変更・ご判断ください）**：
ミックス詳細のフレーバー行は依然 `{f.ratio}g` と**単位gで断定表示**しています。比率で入力された場合「60g」と誤表示されます。
- 案A（推奨・軽微）：詳細も**%表示に統一**し、gは表示しない
- 案B：`ratio_unit`（'g' | 'ratio'）列を追加して入力単位を保持
- 案C：現状維持（こだわり投稿はg前提と割り切る）

**既存仕様を大きく壊す変更のため、STEP 5では実施していません。**
