## 1. mix / combo / 作り方 の現行データモデル（調査結果）

**結論：親子構造は既に「派生（導出）」の形で実装済み。新しい親テーブルは不要。**

| 概念 | 現行実装 | 実体 |
|---|---|---|
| **フレーバーの組み合わせ**（親） | `mixes.combo_key`（text列） | フレーバー集合を正規化した文字列。`brand\|name` を小文字化・**重複/順序/割合を無視**してソート結合（`lib/combo.ts`）。例：`mango + mint` |
| **作り方**（子） | **`mixes` の1行** | コード内で literally `method` と呼ばれる。配合・ボウル・炭・蒸らし・熱カーブを持つ**具体的な一台** |
| **組み合わせページ** | `/combo/[slug]` | `combo_key` が同じ `mixes` を **`GROUP BY combo_key`** で束ねて表示（`buildCombos` / `getComboBySlug`）。「◯通りの作り方」を比較 |

Mango × Mint の例＝現行構造そのまま：

```
combo_key = "mango + mint"        ← 親（フレーバー組み合わせ・仮想。テーブルは無い）
  ├ mixes行A  60:40 / Kaloud / 炭3   ← 作り方（method）
  ├ mixes行B  70:30 / Provost / 炭2  ← 作り方（method）
  └ mixes行C  50:50 / Turkish / 炭3  ← 作り方（method）
```

**含意（王道モデルの再設計）**
- 王道になるのは **combo（親）ではなく、その中の特定の `mixes` 行（作り方）**。
- 前回案 `mix_orthodoxy (mix_id primary key)` は**誤り**。王道の一意性は「1つの `combo_key` につき1つ」であるべき。→ 下の 3 で修正。
- 既存 `national_reps (category, mix_id)` は「味の系統(category)ごとの代表」で、**combo単位の王道とは別軸**。温存し、王道の「候補供給源」に使う。
- **`combos` テーブルは追加しない。** `combo_key` を親キーとして再利用する。

## 2. mix_experiences 修正版スキーマ

`mix_smokes` → **`mix_experiences`**（実体験ログ）。複数回記録可・日時分離・shop_id 反映。

```sql
create table public.mix_experiences (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references public.profiles(id) on delete cascade,
  mix_id  uuid not null references public.mixes(id)    on delete cascade,
  experience_type text not null default 'smoked'
    check (experience_type in ('smoked','made','verified')),  -- 吸った / 作ってみた / 店舗確認済み
  verdict text check (verdict in ('again','good','ok','not_for_me')),  -- また吸いたい/おいしい/普通/好みではない（任意）
  shop_id uuid references public.shops(id) on delete set null,          -- 店舗連携（任意・将来のverified用）
  occurred_at timestamptz not null default now(),  -- 実際に吸った日時
  created_at  timestamptz not null default now(),  -- 記録した日時
  note text
  -- ★ unique(user_id, mix_id) は付けない：同じミックスを何度でも記録可
);
create index on public.mix_experiences (user_id, occurred_at desc);
create index on public.mix_experiences (mix_id);
-- RLS: 本人 insert/update/delete/select。公開集計(吸われた回数)は count RPC 経由
```

### 既存 mix_makes / mix_onsite_ratings の互換方針（コード参照箇所確認済み）
`mix_makes` は `lib/queries.ts` の **8箇所**（王道自動選出の重み・煙道帳・作った数カウント等）、`mix_onsite_ratings` は **6箇所**で参照。いずれも0行なので統合は安全だが、一度に書き換えると壊れるため**段階移行**する。

- 統合方針：`mix_makes` → `mix_experiences(experience_type='made')`、`mix_onsite_ratings` → `mix_experiences(experience_type='verified')`。
- 互換の保ち方（推奨）：`mix_experiences` を追加し、旧2テーブルを**退避→同名の読み取り互換ビュー**にする：
  ```sql
  -- 旧テーブルはリネームして退避し、同名ビューで既存クエリを延命
  create view public.mix_makes as
    select mix_id, user_id, occurred_at as created_at
    from public.mix_experiences where experience_type = 'made';
  ```
  → `lib/queries.ts` の8箇所は当面そのまま動作。落ち着いてから順次 `mix_experiences` 直参照へ置換。
- `mix_onsite_ratings` は `score`/`rated_at` を持つ。スコアは下の4のverified扱い・要判断（当面は verdict のみで開始）。

**確認**：この段階移行（退避→同名ビュー）でよいか。0行なので即DROP＋全参照書換も可能（推奨は互換ビュー）。

## 3. 王道モデル 修正版スキーマ（combo_key を親キーに）

作り方（method＝`mixes`行）を対象に、**推薦は複数可・王道は1組み合わせ1つ**。

```sql
create table public.method_endorsements (
  id uuid primary key default gen_random_uuid(),
  mix_id    uuid not null references public.mixes(id) on delete cascade,  -- 対象の作り方(method)
  combo_key text not null,           -- 親＝mixes.combo_key を複製（王道の一意制約用）
  state text not null default 'candidate'
    check (state in ('candidate','review','certified')),  -- 推薦 / 審査中 / 王道
  proposed_by  uuid references public.profiles(id),  -- 推薦者（プロ/店舗/運営）
  certified_by uuid references public.profiles(id),  -- 認定した運営
  certified_at timestamptz,
  note text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

-- ★ 1つの組み合わせにつき「王道(certified)」は1つだけ
create unique index one_certified_per_combo
  on public.method_endorsements (combo_key) where state = 'certified';

-- 同じ作り方への同一人物の重複推薦を防ぐ
create unique index uniq_endorsement_per_method_proposer
  on public.method_endorsements (mix_id, proposed_by);
-- RLS: 推薦作成=プロ/店舗/運営、certified化=運営(is_admin)のみ
```

- 複数の作り方が「推薦(candidate)」され得る → 運営が1つを「王道(certified)」に昇格。
- `national_reps`（自動選出）は温存し、運営認定の**候補提示**に使う（自動全認定はしない）。
- `combo_key` を親キーに使うため **`combos` テーブルは不要**。作り方編集でフレーバーが変わり `combo_key` が変わるエッジケースは、endorsement側の `combo_key` を同期（トリガ or アプリ側）。

### UI名称（画面表示・DB非依存）
- `candidate` ＝「推薦／まずはこの作り方」
- `certified` ＝「王道」
- `review`（審査中）＝**管理画面のみ**。「王道候補」という事務的表現はユーザー画面で使わない。

## 4. 味覚評価モデル 修正版スキーマ（体験に紐づく・履歴保持）

`mix_taste_votes (mix_id,user_id)` の上書き案を廃止。**体験(experience)に紐づけ、上書きせず履歴として蓄積**。

```sql
create table public.taste_evaluations (
  id uuid primary key default gen_random_uuid(),
  experience_id uuid not null references public.mix_experiences(id) on delete cascade,  -- 「今回吸った体験」に紐づく
  mix_id  uuid not null references public.mixes(id)    on delete cascade,  -- 集計用に複製
  user_id uuid not null references public.profiles(id) on delete cascade,
  sweetness smallint check (sweetness between 1 and 5),  -- 甘さ
  coolness  smallint check (coolness  between 1 and 5),  -- 爽快感
  sourness  smallint check (sourness  between 1 and 5),  -- 酸味
  richness  smallint check (richness  between 1 and 5),  -- 濃厚さ
  heaviness smallint check (heaviness between 1 and 5),  -- 重さ
  created_at timestamptz not null default now(),
  unique (experience_id)  -- 1体験1評価（体験は何度でも作れる＝実質履歴）
);
create index on public.taste_evaluations (mix_id);
-- 平均は mix単位（または combo単位）で unstable_cache + 集計RPC。表示は段階開示（言葉→数値）
```

- 同じミックスを何度吸っても、**その都度の体験に別々の評価が残る**（上書きしない）。
- 平均は「作り方(mix)単位」で算出。将来 combo 単位も `combo_key` join で可能。
- 味系統は既存 `mixes.taste_tags` を継続利用（数値5軸＝強さ、タグ＝系統、で分離）。

### 味覚UI（DB非依存）
- 主表示＝言葉（甘め・爽快・軽め）。
- 詳細表示＝バー（甘さ 4.2/5・爽快感 4.5/5・酸味 2.1/5・濃厚さ 3.8/5・重さ 2.7/5）。
- レーダーチャートは**補助のみ**（初心者向けの主表示にしない）。
