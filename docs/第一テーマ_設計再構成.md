最終更新: 2026-08-18 ／ ステータス: **設計（未実装・コード/DB/SQL/API/UI 変更なし・ヒアリング未実施）**

## 1. ストレステストで判明した前提変更

### 1-1. 2台目のコストの再定義

| | 誤（旧設計） | 正 |
|---|---|---|
| 2台目のコスト | 2〜3時間 | **セッション枠1回＋フレーバーの拘束** |

シーシャを吸う夜は、もともとシーシャのために空けてある。時間そのものは障壁ではない。
本当のコストは3つ。

| コスト | 内容 | UIで解けるか |
|---|---|---|
| ① **セッション枠の消費** | 自宅勢は月4〜12回。8週で8〜24枠。1枠の提供＝体験の5〜25% | ❌ **解けない** |
| ② **フレーバーの拘束** | 参加するには「今夜は DA 100% でよい」必要がある | ❌ **解けない** |
| ③ 生活・環境（片付け・同居人・煙・器材・複数人・営業） | | ❌ ほぼ解けない |

**この3つはUIの問題ではなく、参加者の選び方と、参加の設計（何を要求するか）の問題である。**

### 1-2. 記憶に依存する比較をやめる

2週間前に吸った一台の「甘さ3か4か」を人は覚えていない。本人もそれを分かっている。
→ 絶対評価の引き算をコアにしない。**「前の1台と比べてどうだったか」を直接聞く。**

### 1-3. ★今回いちばん重要な発見：「1台でも価値がある」は、実は難しい

「2台は重いから1台でも価値が出るようにしよう」は自然な発想だが、**コールドスタートでは逆になる。**

| | 必要なデータ | 立ち上げ時（experience 0件）に成立するか |
|---|---|---|
| **2台比較の価値** | **自分の2台だけ** | ✅ **他人が1人もいなくても成立する** |
| **1台の価値（従来案）** | 他人の人数・平均・評価 | ❌ **他人がいないと何も返せない** |

「あなたは32人目です」「平均は3.8です」——これらは**参加者がいて初めて言える**。
第一テーマの開始時点では experience は0件であり、**1台目の価値を他人依存で作ると、最初の数十人には何も返らない。**

→ **1台の価値を「他人の評価」から作ってはいけない。**
→ **「他人がいなくても返せるもの」から作る。**（§3 で設計）

### 1-4. 旧設計から取り下げる記述

| 旧設計の記述 | 変更 |
|---|---|
| 「Primary KPI＝2METHOD以上を作った人数20人（必達）」 | **必達条件から外す。**段階指標へ（§12） |
| 「第一テーマの必須範囲では DB 変更は発生しない」 | **訂正。**直接比較（P0-2）の採用により、**追加2列のDB変更が必要になる**（§10） |
| 「M4 の中核＝あなたの中の比較」 | **中核から外す。**2台目以降の追加価値に降格（§5） |
| 「未完了感（もう1台で比較が出ます）」 | **主要CTAにしない**（§11） |
| 「店舗は1人2METHODが成立してから」 | **保留を解除し、二層構造の一方として最初から設計に含める**（§7・§8） |

## 2. 新しい第一テーマの目的

### 2-1. 検証したい問いを2段に分ける

旧：「煙道では、人が他人の METHOD を試して比較するのか？」（1問・オール・オア・ナッシング）

新：**2つの問いに分ける。**

| | 問い | 答えが NO のときの意味 |
|---|---|---|
| **問い1** | **人は、他人の METHOD を実際に試すのか？** | NO なら煙道は成立しない。**プロダクトの生死** |
| **問い2** | 試した人は、さらに比較までするのか？ | NO でも成立しうる。**比較を煙道側が引き受ける形へ縮退**（§15） |

**分けることの意味**：旧設計は問い1と問い2を同時に問うていたため、
「2台目が出なかった」＝「全部だめ」に見えてしまう。
実際には**問い1が YES で問い2が NO** という結果は、極めて有用な情報である（撤退先が確定する）。

### 2-2. 第一テーマが提供するもの

> **「あなたのいつもの一台を、誰かのやり方に置き換えてみる。」**

- 追加で作れとは言わない（頻度を上げない）
- 投稿しろとも言わない
- 2台作れとも言わない
- **1台でも、そこで完結した価値が返る**

## 3. 1台だけでも成立する体験

### 3-1. 設計原則：他人がいなくても返せるものだけで、1台目の価値を作る

experience 0件の状態でも返せる材料は3つある。

| 材料 | 必要なもの | 他人依存 |
|---|---|---|
| **① 検証対象10件のパラメータ**（＝設計空間の地図） | 10件の method が存在すること | **なし** |
| **② 作り手の意図**（なぜこの炭数なのか） | 作り手が書いたテキスト | なし |
| ③ あなた自身の記録 | 自分の1台 | なし |
| ④ 他人の人数・平均・評価 | 他の参加者 | **あり（後から効く）** |

**①〜③だけで1台目の価値を作る。④は人が増えたら自然に足される。**

### 3-2. ★1台目の完了画面（再設計）

```
──────────────────────────────────
  #03 で1台、記録しました。

  ▼ あなたが作った一台は、ここにいます        ← ★①地図（他人不要）

     炭の数    2個 ━━━━●━━━━━━ 4個
                        ▲ あなた 3個
     蒸らし    3分 ━━━━━●━━━━ 12分
                         ▲ あなた 7分
     詰め方    ふんわり ●━━━━━━ ぎっしり
                    ▲ あなた

     検証対象10件は、この幅の中に散らばっています。
     あなたが試したのは「標準的な熱量・ふんわり」の作り方です。

  ▼ この作り方をつくった人の意図              ← ★②作り手の言葉（他人不要）

     「炭3個・蒸らし7分は、DA のシロップを飛ばしすぎない
       ぎりぎりの熱量です。4個だと最初の10分で香りが飛びます。」
                                    — ◯◯（自宅・4年）

  ▼ あなたの記録                              ← ★③自分のデータ
     判定：おいしかった
     甘さ3 / 重さ4（任意入力ぶん）
     煙道帳に残りました。

  ─────────────────────────────
  ▼ 気が向いたときに                          ← 宿題にしない置き方

     この10件は、炭の数が 2〜4個 に分かれています。
     あなたが試したのは真ん中（3個）。
     両端がどう違うのかは、まだ誰も答えを出していません。

     [ 炭が1つ少ない作り方を見てみる ]
     ※次にシーシャを作るときで大丈夫です
──────────────────────────────────
```

### 3-3. なぜこれで「参加してよかった」になるのか

| 返しているもの | 心理 |
|---|---|
| **地図の中の自分の位置** | 「自分がどこにいるか分かった」＝ 知識が増えた実感。他人が0人でも成立する |
| **作り手の意図** | 「なぜそうするのか」が分かる＝ 今夜の一台が上手くなる。**これが最も実利がある** |
| 自分の記録が残る | 蓄積の始まり |
| 未解決の問いの提示 | 好奇心。**ただし要求はしない** |

**「あなたは32人目です」は入っていない。** 人が増えたら足す。最初から前提にしない。

### 3-4. 人が増えたときに足されるもの（④）

| 条件 | 追加表示 |
|---|---|
| 他に作った人がいる | 「あなたのほかに◯人が試しています」 |
| 評価者3人以上 | 「この作り方の平均：甘さ3.8」（既存の `MIN_RATERS_FOR_AVERAGE = 3`） |
| ペア比較が貯まった | 「この作り方と #07 を両方作った人は、◯人中◯人が #07 を選びました」 |

**段階的に厚くなる設計。**初期の薄さを、地図と作り手の言葉で埋める。

## 4. 他人 METHOD を試す体験（レベル2）

### 4-1. 定義の整理

新設計では、**1台目がすでに「他人の METHOD」である**（検証対象から選ぶため）。
したがって **L1（参加）＝ 問い1「人は他人の METHOD を試すのか」の答えそのもの**になる。

これは旧設計より重要な変化である。旧設計は「2台目で初めてコア仮説が検証される」構造だったが、
新設計では **1台目の時点でコア仮説の半分が検証される。**

### 4-2. 例外経路（自分のやり方から始める人）

自分のやり方に自信がある人（ケースF）は、他人のやり方から始めることに抵抗がある。

```
  基準の1台を選ぶ画面の最下部に、小さく：
  「自分のやり方で始める」→ 5軸だけの最小投稿 → それを1台目にする
```

- 主導線にしない（小さく置く）
- この経路の人は **L1 にカウントしない**（他人の METHOD を試していないため）
- 2台目で検証対象を作った時点で L1 に入る

**この分岐があるおかげで、L1 の数字が「他人の METHOD を試した人」を正確に表す。**

## 5. 2台比較の位置づけ

### 5-1. 必須条件から外す

```
レベル1  1台つくって記録する          → 参加。地図の中の位置＋作り手の意図が返る
レベル2  他人の METHOD を試す          → L1と同じ（1台目が既に他人のMETHOD）
レベル3  2つ以上を作り、直接比較する    → 「あなたの中の比較」が生まれる
レベル4  複数人・複数METHODが蓄積する   → 全国の傾向・ペア比較の集計・王道候補
```

**レベル1で完結してよい。** レベル3は「できる人にとって強い体験」。

### 5-2. レベル3をどう位置づけるか

| 旧 | 新 |
|---|---|
| 2台目は**必須**（KPIの本体） | 2台目は**上位互換の体験**（KPIの上位段） |
| 「もう1台で比較が出ます」＝ 欠けの提示 | 「気が向いたときに」＝ 招待 |
| 完了画面の主役 | 完了画面の**最下部** |

### 5-3. ただしレベル3を諦めない理由

§1-3 の通り、**レベル3の価値は他人が0人でも成立する唯一の価値**である。
コールドスタート期には、むしろレベル3こそが最も濃い体験を返せる。

→ **要求はしないが、たどり着いた人には最大の報酬を返す。**
→ 「宿題にしない」と「諦める」は違う。

## 6. 自宅ユーザーのジャーニー

### 6-1. 前提

- 頻度：月4〜12回。8週で8〜24枠
- 今夜吸いたいフレーバーがある（DA 100% とは限らない）
- 1晩1台。同一夜の比較は**不可能**
- 前回の味は覚えていない
- 記録タイミングは深夜・眠い・飲酒後

### 6-2. ジャーニー

```
[1] トップにテーマ入口（無視できる置き方）
      ↓
[2] テーマページ
    「いつもの一台を、誰かのやり方に置き換えてみませんか」
    ★「追加で作ってください」とは言わない
      ↓
[3] 3問（ボウル／熱管理／炭の数）＋「わからない」→ 1件に絞る
      ↓
[4] 作り始めに [作った] 1タップ  ★記録を吸い終わりに集約しない
      ↓
[5] 2.5時間。アプリは何もしない。通知もしない
      ↓
[6] 吸い終わり：判定4択（任意）／味5軸（任意・あとででも可）
      ↓
[7] ★1台目完了画面（§3-2）
    地図 ＋ 作り手の意図 ＋ 自分の記録 ＋ 気が向いたときの1件
      ↓
[8] 数日〜数週間の空白
    ★トップ最上部と煙道帳の先頭に「見てみた作り方」が残っている
    ★通知はしない
      ↓
[9] 次のセッションで作る気になれば → 2台目
    記録時に「前の1台と比べてどうでしたか？」（§10）
      ↓
[10] 直接比較が返る（レベル3の報酬）
```

### 6-3. 自宅ユーザー向けの設計要件

| # | 要件 | 理由 |
|---|---|---|
| 1 | **頻度を上げさせない** | 「いつもの1台を置き換える」であって「追加で作る」ではない |
| 2 | **記録を分割する** | 作り始めに1タップ／味は後日可 |
| 3 | **完了画面に依存しない** | 「次の1台」はトップと煙道帳にも常設。数日後に消えない |
| 4 | **通知しない** | 月数回の行動に通知は噛み合わない |
| 5 | **絶対評価の記憶を要求しない** | 直接比較で聞く |
| 6 | **1台で完結する** | 2台目を前提にした画面にしない |

## 7. 店舗ユーザーのジャーニー

### 7-1. 店舗の構造的な違い（最重要）

**店舗では「作る人」と「評価する人」を分離できる。** 自宅では同一人物である。

| | 自宅 | 店舗 |
|---|---|---|
| 作る人 | 本人 | スタッフ（経験量が桁違い） |
| 評価する人 | 本人 | **客（独立した舌）** |
| 同一夜の複数台 | 不可能 | **可能** |
| 記録する時間 | 深夜・疲労 | **客は3時間ひまで、スマホがある** |
| 記憶への依存 | 数日〜数週間 | **ほぼゼロ（直後に比較できる）** |

**同じ夜に A を吸い、B を吸い、その場で比べる。これは店舗でしか起きない。**
記憶に依存しない比較データは、店舗からしか出てこない。

### 7-2. 誰が記録するのか（設計の核心）

**スタッフに記録させない。** 営業中に1台ごとにアプリを開く運用は続かない。

```
  スタッフ … 作るだけ（普段の仕事のまま）
  客       … 卓上QRから記録する（3時間ひまである）
```

`mix_experiences.verification_type = 'shop_qr'` と `shop_id` は**実装済み**。

### 7-3. 店舗ジャーニー（2パターン）

**パターンA：客が2台吸う（最も価値が高い）**

```
[1] 卓上に「今月の煙道検証」のカード
[2] 客が1台目を注文（METHOD #03 でスタッフが作る）
[3] QRから記録（ログインが必要 ← 摩擦。§7-5）
[4] 吸う（1〜1.5時間）
[5] 2台目を注文（METHOD #07 ＝ 炭の数だけ違う）
[6] 記録時に「さっきの #03 と比べてどうでしたか？」
    ★記憶が新しいうちの直接比較。最高品質のデータ
[7] その場で結果が返る
```

**パターンB：スタッフが試作時間に比較する**

```
[1] 開店前・閑散時にスタッフが #03 と #07 を続けて作る
[2] スタッフ自身が比較を記録
[3] 経験量の裏付けがある比較データが1晩で複数件生まれる
```

→ パターンB は速いが、**1人の舌に偏る**（§7-4）。

### 7-4. 店舗を入れることのリスク（結論ありきにしない）

| リスク | 深刻度 | 対処 |
|---|---|---|
| **1人のスタッフの舌にデータが支配される** | 高 | 集計を**ユーザー単位で重み付け**（既存 `mix_taste_summary` と同じ考え方）。ペア比較にも同じ扱いが要る（未設計） |
| **店舗の器材・環境が家庭と違う** | **高** | 業務用ステム・高性能HMD前提の METHOD が王道になると、**家庭で再現できない王道**になる。検証対象の選定で「特殊器材を要求しない」を必須にする |
| 「店の宣伝」に見え、一般参加者が引く | 中 | 店舗名を前面に出さない。METHOD の作り手として並列に扱う |
| 店舗が1軒抜けるとデータが止まる | 中 | 二層構造（§8-C）で片肺にしない |
| 客の登録が壁になる | **高** | §7-5 |

### 7-5. 未解決：客の記録にはアカウントが要る

QR → 記録には**ログインまたは新規登録**が必要。
ゲストモード／匿名認証は `CLAUDE.md` の「今は作らないもの」に入っている。

| 案 | 評価 |
|---|---|
| 客に登録してもらう | 摩擦は大きいが、**煙道の会員が増える**という副次価値がある |
| スタッフが客の感想を代理記録 | 記録は増えるが、**自己申告の主体がずれる**（誰の舌か不明になる）。推奨しない |
| ゲストモードを作る | 方針変更が必要。**第一テーマの範囲では判断しない** |

→ **未決定事項。** 店舗パターンAを本気でやるなら、ここを先に決める必要がある。

## 8. A/B/C モデル比較

| 観点 | **A：自宅中心** | **B：店舗中心** | **C：二層構造** |
|---|---|---|---|
| 参加ハードル | **高**（枠＋フレーバー拘束＋器材＋片付け） | 低（スタッフはどうせ作る）／ただし**記録**の壁は高い | それぞれに合った入口を用意できる |
| データ品質 | 中（記憶依存の比較。環境がばらつく） | **高**（同一夜比較・経験量の裏付け） | **高**（店舗の高密度＋自宅の多様性） |
| データ量 | **低**（8週で1人2〜3枠が限界） | **高**（1晩で複数件） | 中〜高 |
| 継続性 | 低〜中（枠が空かないと止まる） | 中（店の都合次第。1人抜けると止まる） | **中〜高**（片方が止まっても残る） |
| 思想との整合 | **高**（みんなでつくる） | 中（「みんな」ではない。権威に寄る危険） | **高** |
| 王道への到達 | 遅い | 速いが**偏った王道**になる危険 | 速さと妥当性を両立しうる |
| 一般ユーザーへの拡張性 | **高**（最終的にここが本体） | **低**（家庭で再現できない王道は広がらない） | **高** |
| 設計コスト | 低 | 低 | 中（2系統に見える） |

### 推奨：**C（二層構造）**

- **店舗＝高密度データ生成層**：同一夜比較・経験量。少数でよい（1〜3店）
- **自宅＝広い参加層**：多様な環境・多様な舌。1台ずつ長期に貯まる
- 店舗のデータが「家庭で再現できるか」を自宅層が検証する ← **この相互検証が C の最大の価値**

### C を選んでも実装は1系統でよい（重要）

C の欠点は「設計が2系統になる」ことだが、**実装は分岐しない。**

| | 自宅 | 店舗 |
|---|---|---|
| 使う機能 | 「作った」を記録 | **同じ機能を同じ夜に2回使うだけ** |
| 直接比較 | 数日後に聞く | 同じ夜に聞く |
| 違い | `shop_id` と `verification_type='shop_qr'` が付くかどうか（**既存実装**） | |

→ **同一夜比較のための専用機能は要らない。**「occurred_at が近い2件」であるだけ。
→ C を選ぶことによる追加実装コストは、ほぼゼロ。

### C を採る場合の注意

**店舗を「先に」やらない。同時に置く。**
店舗を先行させると、初期データが店舗環境に偏り、そこから作られた王道が家庭で再現できなくなる。
逆に自宅を先行させると、記憶依存の弱い比較データしか集まらない。
**両方を最初から並走させ、店舗のデータが自宅で再現されるかを見る。**

## 9. 「次の1台」の役割

### 9-1. 役割の再定義

| 旧 | 新 |
|---|---|
| 次に作るべきもの（宿題） | **気が向いたときの選択肢（招待）** |
| 完了画面の主役 | 完了画面の**最下部** |
| 「もう1台で比較が出ます」 | 「両端がどう違うのかは、まだ誰も答えを出していません」 |

### 9-2. 提示の条件（旧設計を維持）

- 差分が1軸（かつ**知覚できる幅**があること）
- 変更コストが低い（炭の数・初期加熱・詰め方）
- まだ試していない
- 特殊器材を要求しない
- 比較価値が高い（運営の内部条件。文面には出さない）

### 9-3. 自動推薦は作らない

**初期は運営が人間の判断で候補を選ぶ。**

理由：
- どの差分が実際に試されるか、どの METHOD が避けられるかを、**運営が学習する必要がある**
- アルゴリズムを先に作ると、その学習機会を失う
- 検証対象が10件・参加者が数十人の規模では、**手で選んでも運用できる**

→ 第一テーマでは「差分が1軸で変更コストが低いもの」を**運営が事前に決めた対応表**で出す。
　 （例：#03 を作った人 → #07 を出す、という固定の対応表）

### 9-4. 実行を求めない置き方

```
  [ 炭が1つ少ない作り方を見てみる ]
  ※次にシーシャを作るときで大丈夫です
```

- 「今すぐ作る」と言わない
- 「見てみる」（＝閲覧）を CTA にする。作ることを CTA にしない
- 見た結果、作らなくてもよい

## 10. 直接比較の UX

### 10-1. 何を聞くか

2台目以降の記録時に、**1〜2タップで答えられる質問**を1つ。

```
  ▼ さっき（前回）作った #03 と比べて、どうでしたか？

     [ #07 の方が好き ]  [ 同じくらい ]  [ #03 の方が好き ]

  ▼ どこが違いましたか？（任意・複数可）
     [ 甘い ] [ 軽い ] [ 濃い ] [ 涼しい ] [ 重い ] [ 分からない ]
```

### 10-2. 絶対評価との比較

| | 5軸×2台の引き算（旧） | 直接比較（新） |
|---|---|---|
| 入力コスト | 10タップ | **1〜2タップ** |
| 記憶への依存 | 2週間前の絶対値 | 「前より甘い」は思い出しやすい |
| 人間の得意不得意 | 絶対評価は苦手 | **相対評価は得意** |
| 「差が無い」の表現 | できない | **「同じくらい」で明示できる** |
| 将来の王道判定 | 平均の比較（ばらつきに弱い） | **ペア比較の蓄積（順位付けに強い）** |

**5軸は残す。任意のまま。**ただし「あなたの中の比較」の成立条件から外す。

### 10-3. ★DB 変更が1つ必要になる（旧設計の訂正）

直接比較は「2つの experience の関係」であり、既存カラムから導出できない。
**旧設計の「第一テーマの必須範囲では DB 変更は発生しない」は、この採用により成り立たなくなる。**

必要な変更（**最小形・実装はしない**）：

```
mix_experiences に nullable な2列を追加するだけで足りる想定

  compared_to_mix_id   uuid  null   何と比べたか
  comparison           text  null   前より良い / 同じくらい / 前より良くない
```

- **追加のみ**（既存カラム・既存データに影響しない）
- RLS は既存の「自分の experience のみ」がそのまま効く
- 別テーブルにする案もあるが、experience 1件に付随する属性なので同一テーブルが素直

**この判断は実装前にユーザー確認が必要**（§19）。

### 10-4. 「同じくらい」を歓迎する

差が出ないことは失敗ではない。

```
  「違いは分かりませんでした」も、立派な記録です。
  炭1個では、あなたには差が出ないということが分かりました。
```

**差が出なかった場合の受け皿がないと、そこで体験が終わる。**

## 11. 予想機能の扱い

### 11-1. 概要

1台目の記録後に「炭を1つ減らすと、どう感じると思いますか？」を1タップで聞き、
2台目を作ったときに答え合わせをする。

### 11-2. 期待できること

| 効果 | 説明 |
|---|---|
| **未完了感を好奇心に変える** | 「あと1台やって」は他人からの要求。「自分の予想が当たるか」は自分の問い |
| **完了画面がその場で完結する** | 1タップの行動が用意され、「見るだけ」で終わらない |
| **味覚入力がなくても報酬が返る** | 「当たった／外れた」は必ず返せる |
| **外れた方が面白い** | 予想外＝発見。失敗にならない |
| **「差が無い」も回収できる** | 「変わらない」を選べる |

### 11-3. 懸念（実装を今決めない理由）

| 懸念 | 内容 |
|---|---|
| **宿題感が完全には消えない** | 「予想する」は「次に作る」を前提にしている。招待の言葉に留める必要がある |
| **外した人が萎縮する可能性** | 「自分は味が分かっていない」と感じさせない文言が要る |
| **効果が仮説** | 実際に効くかは未検証 |
| 1台目完了画面が重くなる | 地図＋作り手の意図＋予想 は情報が多い。優先順位の再検討が要る |

### 11-4. 判断

> **実装しない。ただし、実装せずに検証する。**

- 第一テーマの最初の参加者数人に、**運営が口頭・DMで同じ問いを投げる**
- 「炭を1つ減らしたらどうなると思いますか？」→ 実際に作ってもらう → 答え合わせ
- **反応が良ければ実装する。悪ければ捨てる。**

実装コストゼロで仮説を検証できる。**先に作らない。**

## 12. KPI 再設計

### 12-1. 段階指標（レベル構造に対応）

| 段 | 指標 | 定義 | 何が言えるか |
|---|---|---|---|
| **L1** | **テーマ参加者数** | 検証対象 METHOD を1台以上作って記録したユニークユーザー | **問い1「人は他人の METHOD を試すのか」の答え** |
| **L2** | 継続者数 | テーマ内で2台以上作った人（同じ METHOD でも可） | テーマへの再訪が起きるか |
| **L3** | **比較者数** | **異なる2つ以上**の METHOD を作り、直接比較を記録した人 | **問い2「比較までするのか」の答え** |
| L4 | 蓄積 | ペア比較の件数／再現者数／リピート数 | 王道に必要なデータ量 |

### 12-2. 決定的な指標は「比率」

```
  L1 ＝ 何人が試したか        （問い1）
  L3 ／ L1 ＝ 試した人のうち、比較まで進んだ割合   （問い2）★
```

**L3/L1 が第一テーマの本当の答えである。**

| L3/L1 | 解釈 | 次の行動 |
|---|---|---|
| **30%以上** | コア体験が成立している | 現行設計を継続。次テーマへ展開 |
| 10〜30% | 一部で成立。比較は少数の体験 | 比較を主導線から外し、L1 を最大化する設計へ |
| **10%未満** | **比較は起きない** | **撤退先へ（§15）。煙道が集計する形に縮退** |

### 12-3. 参考値（合否ではなく診断）

8週での目安。**達成できなければ失敗、という使い方をしない。**

| 指標 | 目安 | 根拠 |
|---|---|---|
| L1 参加者 | 30〜50人 | 母集団（自宅で月4回以上作る人＋店舗スタッフ）への到達可能性は未検証 |
| L2 継続者 | L1 の 50% | — |
| L3 比較者 | L1 の 30〜40%（＝10〜20人） | 旧設計の「20人」はここに相当する。**必達ではなく目安に降格** |
| L4 ペア比較 | 30件以上 | 検証対象10件のうち主要ペアに各3件程度 |

### 12-4. Guardrail と危険指標（維持）

| 指標 | 危険な状態 |
|---|---|
| **METHOD投稿者数 ＞ L3 比較者数** | 投稿サイト化。投稿導線を弱める |
| 投稿だけして体験しない人の割合 | 高い＝見せたいだけの場 |
| 1 METHOD に再現が集中しすぎる割合 | 高すぎると比較が成立しない |
| **地図が偏っている**（検証対象の5軸が散らばっていない） | 比較の前提が崩れる（§14-3） |

## 13. 王道への接続

### 13-1. 自然に貯まるか

| 王道に必要なデータ | 通常行動で生まれるか |
|---|---|
| 再現者数（作者以外が作った人数） | ✅ L1 で自動的に増える |
| リピート数 | ✅ 気に入れば繰り返す |
| **どちらが好まれたか（ペア比較）** | ✅ **L3 の直接比較でそのまま生まれる** |
| 味の評価（5軸） | 🔺 任意入力。記入率に依存 |
| 第三者比較（再現忠実度） | — 第一テーマでは実施しない |

**ユーザーは王道のために行動しない。「どっちが好きだったか」に答えるだけで、王道に必要なデータが貯まる。**
この構造は成立している。

### 13-2. ペア比較の限界（正直に記録する）

このデザインで集まるペア比較は**完全なグラフにならない。**

- 人は「1台目 → 推薦された2台目」を比較する
- したがって比較の辺は、**人気のある起点 METHOD を中心とした星形**になる
- 「#07 と #11 のどちらが良いか」を直接比べた人は少ないか、いない

→ 将来的に順位付けをするなら、この偏りを前提にした手法が要る。
→ **第一テーマでは順位を出さない。** データを貯めるだけ。

### 13-3. 人気投票化しないための線（維持）

- ペア比較の**勝率を UI に出さない**（運営の判断材料に留める）
- ランキング画面を作らない
- 集計値がそのまま王道にならない。門を通った候補を煙道が確認して認定する
- ペア比較の重みは**ユーザー単位**（1人が20回比較しても、その人の影響が20倍にならないようにする。§7-4）

### 13-4. 門の条件は見直しが必要（未決定）

旧設計の門は「taste 評価者3人以上」を含む。
5軸を必須依存から外した以上、**ペア比較の件数を条件に加えるか、置き換えるかは未決定。**
第一テーマ中は判定を急がず、データが出てから決める。

## 14. 投稿者と検証者

### 14-1. 第一テーマ期間中は、投稿が増えなくてよい

- 検証対象は8〜12件で**固定する設計**（増やしたくない）
- 8週で必要な METHOD は**事業側が用意する**（創設作り手）
- **投稿が増えないことは失敗条件に入っていない**

→ 投稿者と検証者のバランスは、**第二テーマ以降の問題**。
　 いま解こうとすると投稿導線を強め、クックパッド化を招く。

### 14-2. 守る線

```
  METHOD投稿者数 ＞ L3 比較者数  → 投稿導線を弱める。METHOD を増やす施策は打たない
```

### 14-3. ★検証対象の選定基準に「散らばり」を追加する（新規）

§3 で1台目の価値を「地図の中の位置」から作ると決めた以上、**地図が成立していなければならない。**

検証対象10件が全部「炭3個・ふんわり」なら、地図は1点に潰れ、
1台目の価値も、2台目の差分も、比較そのものも成立しない。

**検証対象の選定基準（3つ）**

| # | 基準 | 理由 |
|---|---|---|
| 1 | 差分5軸（ボウル／詰め方／HMD／炭の数／初期加熱）がすべて埋まっている | 差分を名指しできない method は比較できない |
| 2 | 特殊器材を要求しない | 実行可能性。**店舗環境に依存する王道を作らないため**（§7-4） |
| 3 | **★軸ごとに値が散らばっている** | 例：炭の数が2〜4個、蒸らしが3〜12分に分布していること。**1軸だけ違うペアが複数存在すること** |

**基準3は新規で、かつ第一テーマの成立に必須。**
METHOD を集めるときに「良い作り方を10件」ではなく、**「散らばった10件」**を集める必要がある。

## 15. 失敗時の撤退先

### 15-1. 撤退先の形

L3/L1 が 10%未満だった場合＝「試すが比較しない」。
このとき**ユーザーに比較を要求するのをやめる。**

```
  ユーザー：1台を試す → 記録する（判定・味覚は任意）
  煙道側　：全ユーザーの記録を集計する
  返すもの：「この作り方は、こういう評価を受けています」
           「炭3個の作り方は、2個より『甘い』と答えた人が多いようです」
  次　　　：「次はこの作り方を試してみませんか」
```

比較の主体が**ユーザーから煙道へ移る**だけで、ユーザーの行動は「1台試して記録する」のまま。

### 15-2. 撤退コストの確認

| 項目 | 撤退時にどうなるか |
|---|---|
| `mix_experiences` | **そのまま使える**（experience_type / verdict / occurred_at） |
| `taste_evaluations` | **そのまま使える**（集計の主材料になる） |
| 直接比較の2列（§10-3） | **使わなくなるが、害はない**（nullable の追加列） |
| 検証対象10件 | そのまま使える |
| 地図（1台目完了画面） | **そのまま使える**（他人依存でないため） |
| 作り手の意図 | そのまま使える |
| 「次の1台」 | そのまま使える（推薦理由が「差分」から「集計」に変わるだけ） |

→ **データモデルの破壊は起きない。UI の文言と集計ロジックが変わるだけ。**
→ **撤退コストが小さいことが、現行設計を試してよい根拠でもある。**

### 15-3. さらに下の撤退先

L1 すら集まらない（問い1が NO）場合＝「人は他人の METHOD を試さない」。
このときはテーマ固定型そのものが否定される。
→ **プロダクトの問題ではなく、獲得チャネルまたは前提の問題**として扱い、設計に戻らない。

## 16. 決定事項

1. 2台比較を**第一テーマの必須条件から外す**。レベル1〜4の段階構造にする
2. **1台目の価値を「他人の評価」から作らない。** 地図（設計空間での位置）＋作り手の意図で作る
3. 検証したい問いを**2段に分ける**（問い1：試すか／問い2：比較するか）
4. 2台目以降の比較は**直接比較**（前の1台と比べてどうか）で聞く。絶対評価の引き算をコアにしない
5. 5軸味覚評価は残すが、**「あなたの中の比較」の成立条件から外す**
6. 「未完了感」を主要 CTA にしない。「気が向いたときに」の招待にする
7. 「次の1台」の CTA は**「見てみる」**（閲覧）であって「作る」ではない
8. 自動推薦アルゴリズムを作らない。**運営が事前に決めた対応表**で始める
9. **二層構造（モデルC）を採用**。店舗と自宅を並走させる。店舗を先行させない
10. 店舗ではスタッフに記録させない。**客が記録する**（既存の shop_qr を使う）
11. 検証対象の選定基準に**「軸ごとに値が散らばっていること」**を追加する
12. 検証対象は特殊器材を要求しない（**家庭で再現できない王道を作らないため**）
13. KPI は段階指標にする。決定的な指標は **L3/L1**
14. 旧「2METHOD以上20人」は**必達条件から目安へ降格**
15. ペア比較の勝率を UI に出さない。ランキング画面を作らない
16. ペア比較の重みは**ユーザー単位**にする
17. 予想機能は**実装しない。運営が手動で検証する**
18. 記録を分割する（作り始めに1タップ／味は後日可）
19. 通知しない
20. 第一テーマ期間中、投稿が増えないことは失敗条件にしない

## 17. 仮説（検証対象。実装ルールに固定しない）

1. **地図（設計空間での自分の位置）は、1台だけの参加者にとって十分な報酬になる** ← 新設計の中心仮説
2. **作り手の意図（なぜこの炭数か）は、地図より強い報酬かもしれない**（実利があるため）
3. 直接比較（1〜2タップ）なら、記憶が曖昧でも答えられる
4. 「気が向いたときに」の招待は、「もう1台で比較が出ます」より離脱を減らす
5. 店舗の客は、卓上QRから記録するために**登録までしてくれる**
6. 店舗で2台続けて吸う客が、一定数存在する
7. 予想 → 答え合わせは、未完了感より強い動機になる
8. 検証対象10件を「散らばらせる」ことが、実際に可能である（作り手がそう作ってくれる）
9. 家庭と店舗で、同じ METHOD が同じように評価される（**外れたらそれ自体が重要な発見**）
10. L3/L1 が 30% を超える

| 2 | `MadeButton` に判定4択と味覚入力を足してよいか | 第一テーマの前提条件。SmokedButton と同じ構成 |
| 3 | `comboHref` / `combo/[slug]` のリダイレクト例外化 | テーマページに到達できない既存の制約 |
| 4 | **検証対象10件を「散らばらせる」方針でよいか** | 「良い作り方10件」ではなく「散らばった10件」を集めることになる。作り手集めの方針が変わる |
| 5 | 店舗を自宅と**並走**させてよいか | 「店舗は後」という旧方針の変更 |
| 6 | 店舗の客に登録を求めてよいか | ゲストモードを作らない方針との整合 |
| 7 | 予想機能を「手動で検証してから実装」でよいか | 実装順序の判断 |
| 8 | KPI を L3/L1 中心にしてよいか | 「20人必達」からの変更 |

## 20. 最終判断

### ✅ いま実装してよいもの

| 項目 | 理由 |
|---|---|
| `MadeButton` の判定4択＋味覚入力 | **どの設計変種でも必要。**撤退先でも使う |
| `comboHref` / `combo/[slug]` のリダイレクト例外化 | テーマが何であれ必要。既存の制約解除 |
| 段階指標（L1〜L4）の集計クエリ | 測定できなければ何も判定できない |

**この3つは、第一テーマが DA でなくても、テーマ固定型を採らなくても、撤退先へ行っても無駄にならない。**

### ⚠️ 確認を得てから実装してよいもの

| 項目 | 確認事項 |
|---|---|
| 直接比較（`mix_experiences` に2列追加） | §19-1。**旧設計の「DB変更なし」の訂正を含む** |
| 1台目完了画面（地図＋作り手の意図） | §19-4（散らばりの方針）が決まってから。地図は検証対象の性質に依存する |

### ⛔ まだ実装してはいけないもの

| 項目 | 理由 |
|---|---|
| テーマページの本実装 | 問いの文言・検証対象10件が未確定 |
| **予想機能** | 効果が仮説。**手動で検証してから**（§11-4） |
| 自動推薦アルゴリズム | 運営が学習する機会を失う。対応表で始める（§9-3） |
| 店舗導線（QR・客の記録） | 登録の扱いが未決定（§7-5） |
| 王道の門の判定 | ペア比較前提の見直しが未了（§13-4） |
| METHOD の大量投入 | 方針として不採用 |

### 🚧 UI では解決できない制約（UI で解こうとしない）

| 制約 | 唯一の解 |
|---|---|
| **「今夜は DA 100% でよい」と思えるか** | **参加者の選び方。**ヒアリングでしか分からない |
| セッション枠が月4〜12回しかない | 頻度を上げさせない設計にするしかない（要求を減らす） |
| 片付け・同居人・煙・住環境 | 解けない。**店舗経路が代替になる** |
| 複数人で吸うとき、同席者の希望が優先される | 解けない（「1人1 METHOD ずつ作る」提案は P2 のまま） |
| 器材を持っていない | 変更コスト0の軸を優先することで**部分的に**回避 |

### 🔧 UI で解決できる制約

| 制約 | 解 |
|---|---|
| 前の味を覚えていない | 直接比較で聞く（§10） |
| 5軸の入力が面倒 | 必須依存から外す（§10-2） |
| 記録タイミングが悪い | 記録を分割する（§6-3） |
| 「次の1台」を忘れる | トップ・煙道帳に常設 |
| 1台だけでは何も返らない | 地図＋作り手の意図（§3） |
| 差が分からなかった | 「同じくらい」を用意し、成果として返す（§10-4） |
| 上級者が他人のやり方から始めたくない | 「自分のやり方で始める」の例外経路（§4-2） |
