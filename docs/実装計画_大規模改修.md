## STEP 1 — 現状分析（既存実装の棚卸し）

### 技術スタック
- **Next.js 16.2.3 App Router**（カスタム版。`node_modules/next/dist/docs/` を実装前に必読）。ISR は `export const revalidate`、公開キャッシュは `unstable_cache` + `createPublicClient`（cookieless anon）。
- **Supabase**（project `zjdxhvggsqxscblmfutw`）：Postgres + RLS + SECURITY DEFINER RPC。認証は `@supabase/ssr` cookie クライアント（`lib/supabase/server.ts`）。
- **Tailwind v4**（`@theme` in `globals.css`）。和トークン（朱=seal / 苔緑=ember / 墨 / 和紙bg / 明朝 Shippori Mincho）導入済み。
- デプロイは Vercel（単一 "Vercel" ステータス）。

### 主要画面（`app/` の実在ルート）
検索 `search`・ミックス詳細 `mix/[id]`・投稿 `post`（`mix-form`＝こだわり / `simple-mix-form`＝かんたん）・編集 `mix/[id]/edit`・マイページ `mypage`・棚 `shelf`・王道 `national`・ランキング `ranking`・コンボ `combo/[slug]`・店舗 `shop/[id]`＋`manage`＋`shops`・ガイド `guide`・ボウル/HMS/ブランド別図鑑・タイムライン・通知・管理 `admin`。

### DB 現状（31テーブル・行数）
| 分類 | テーブル | 状態 |
|---|---|---|
| ミックス核 | `mixes`(8)・`mix_flavors`(15)・`flavors`(86) | ✅ 充実。`mixes` に配合/ボウル/HMS/炭/蒸らし/熱カーブまで完備、`taste_tags`(=味系統タグの土台)あり |
| 吸う・作る | `mix_makes`(0)=**作った**・`mix_onsite_ratings`(0)=**実地/店舗評価**(score,shop_id) | 🟡 「作った」と「店舗評価」はあるが、**最軽量の"吸った"自己申告テーブルが無い** |
| 王道 | `national_reps`(4)=自動選出スナップショット(category,mix_id)・`national_reps_meta`(1)=スロットル | 🟡 **候補→運営確認→王道 の状態機械が無い**。今は自動計算のみ |
| 交流 | `likes`(1)・`comments`(2)・`bookmarks`(0)・`follows`(0)・`notifications`(0) | ✅ |
| 店舗 | `shops`(0)・`shop_members`(0)・`shop_flavors`(0) | 🟡 骨格のみ（V1は深追いしない方針と合致） |
| その他 | `shelf`(4)・`pro_applications`(1)・`ideas`系・`mix_names`系・`flavor_ratings`(0)・`mix_photos`(0) 等 | 混在 |

### 新要件に対する 5つの主要ギャップ
1. **最軽量「吸った」記録が無い** — 現状 `mix_makes`(作った)＝再現、`mix_onsite_ratings`(店舗)＝実地の2段しかなく、コア指標(NSM=月間吸った登録数)の受け皿が欠落。
2. **味覚5軸(甘さ/爽快感/酸味/濃厚さ/重さ)のスキーマが無い** — `taste_tags`(味系統)はあるが数値5軸が未定義。
3. **王道の状態機械が無い** — `王道候補`(プロ/店舗/運営推薦)→`運営確認`→`王道`(認定) の3状態と「1ミックス1公式王道」制約が未実装。今は `national_reps` の自動計算のみ。
4. **作り方ごとの属性タグが無い** — `mixes` に 初心者向け/濃厚/軽め/爽快/HMD種別/ボウル種別 を裏で持つ列が無い。
5. **作り手プロフィール実績の集計が無い** — 投稿数以外（王道獲得/実吸評価数/再現回数）を出す集計ソースが未整備。

### 🔴 先に判断が必要なセキュリティ所見（実装計画とは別に要決定）
`public.national_reps_meta` は **RLS が無効**（他30テーブルは有効）。スロットル用に作成した際に RLS を付け忘れたもの。書込関数は SECURITY DEFINER のため機能は維持されるが、anon から直接読める状態。**自動修正はせず**、以下を提示（承認後に適用）：
```sql
ALTER TABLE public.national_reps_meta ENABLE ROW LEVEL SECURITY;
-- 参照は不要（内部メタ）。読取ポリシーは付けない＝一般クライアントからは不可視に。
```

## STEP 3 — DB変更案（**全て追加(additive)・破壊的変更なし**）

> 方針：既存列・既存テーブルは**削除も改名もしない**。新テーブル/新列の追加のみ。RLSは各テーブルに付与。

### ① 「吸った」最軽量記録（P0・最重要＝NSMの受け皿）
```sql
-- 自己申告の「吸った」。星/コメント/写真/味覚は任意
create table public.mix_smokes (
  id uuid primary key default gen_random_uuid(),
  mix_id uuid not null references public.mixes(id) on delete cascade,
  user_id uuid not null references public.profiles(id) on delete cascade,
  verdict text check (verdict in ('again','good','ok','not_for_me')), -- また吸いたい/おいしい/普通/好みではない（任意）
  tier text not null default 'smoked' check (tier in ('smoked','made','verified')), -- 吸った/作ってみた/店舗確認済み
  created_at timestamptz not null default now()
);
-- RLS: 本人insert/select、公開集計は count のみ RPC 経由
```
> 補足：`made`(作ってみた) は既存 `mix_makes` と重複しうるため、**`mix_makes` を廃止せず** `mix_smokes.tier='made'` に一本化するか、`mix_makes` を集計ビューで包む案の2択。**要判断**（推奨：新テーブルに寄せ、`mix_makes` は読み取り互換ビューで温存）。

### ② 味覚5軸（P1・実吸評価の平均）
```sql
-- 実際に吸った人が付ける5軸（任意入力）。投稿者自己申告に依存しない
create table public.mix_taste_votes (
  mix_id uuid references public.mixes(id) on delete cascade,
  user_id uuid references public.profiles(id) on delete cascade,
  sweetness smallint check (sweetness between 1 and 5),
  coolness  smallint check (coolness between 1 and 5),
  sourness  smallint check (sourness between 1 and 5),
  richness  smallint check (richness between 1 and 5),
  heaviness smallint check (heaviness between 1 and 5),
  created_at timestamptz default now(),
  primary key (mix_id, user_id)
);
-- 平均は unstable_cache + RPC で集計表示。taste_tags(味系統)は既存列を継続利用
```

### ③ 王道の状態機械（P0・「候補→運営確認→王道」）
```sql
-- 1ミックス1公式王道。自動全認定はしない
create table public.mix_orthodoxy (
  mix_id uuid primary key references public.mixes(id) on delete cascade,
  makeup_mix_id uuid references public.mixes(id), -- どの作り方が王道か
  state text not null default 'candidate' check (state in ('candidate','review','certified')),
  proposed_by uuid references public.profiles(id),
  certified_by uuid references public.profiles(id), -- 運営
  certified_at timestamptz,
  created_at timestamptz default now()
);
-- 既存 national_reps(自動選出)は「候補の供給源」として残す。認定は運営操作
```

### ④ 作り方ごとの属性タグ（P0の裏・表示はP1）
```sql
-- 既存 mixes に追加（additive）。初心者向け/濃厚/軽め/爽快/HMD/ボウル種別
alter table public.mixes add column if not exists brew_attrs text[] default '{}';
```
> ボウル種別/HMD種別は既存 `bowl_type`/`hms_type` を流用可。`brew_attrs` は「初心者向け/濃厚/軽め/爽快」などの評価系属性を裏で保持。

### ⑤ 作り手実績（P1・集計ビュー、テーブル増やさない）
```sql
create view public.maker_stats as
select author_id,
  count(*) as posts,
  (select count(*) from public.mix_orthodoxy o
     join public.mixes mm on mm.id=o.mix_id where mm.author_id=m.author_id and o.state='certified') as orthodoxy_wins
from public.mixes m group by author_id;
-- 実吸/再現数は mix_smokes 集計を後付け
```

### ⑥ セキュリティ（STEP 1 の所見・**要承認**）
```sql

```

## STEP 4 — 画面・UX変更案（和の世界観 × モダンな操作性・段階開示）

### トップ `app/page.tsx`
- **主目的＝今日の一台を見つける**。上から：`気分 / 手持ちフレーバー / フレーバー名` の入口 → **今日の王道**（1台を大きく）→ 人気 → 店舗/ガイド/ランキングは下段。絵文字は使わず線アイコン＋明朝＋余白。

### ミックス詳細 `app/mix/[id]`（段階開示の核）
1. **結論**：🏆王道 or 候補バッジ ＋「まずこの作り方」（配合・ボウル・炭・蒸らし）※既存の"まずこの作り方"カードを流用
2. **なぜ**：実吸/再現の支持、味覚を**言葉で**（「甘め・爽快・軽め」）
3. **詳細**：`<details>` 展開で熱管理カーブ・g・HMD・炭移動・味覚5軸の数値
- ボタン：**吸った**(最軽量) → 「どうだった？」4択。星/コメント/写真/味覚は「詳しく残す」で任意展開。

### 投稿（3類型に整理）
- A **吸った記録**（`smoked-button` から即時）
- B **かんたん投稿**（既存 `simple-mix-form`：フレーバー＋比率＋一言）
- C **こだわり投稿**（既存 `mix-form`：全詳細＋`brew_attrs` を裏で入力）

### マイ煙道 `app/mypage`
- 煙道帳を **吸った / 作ってみた / 店舗確認済み** の3層で表示（既存セクション拡張）。保存/投稿/自分の評価も集約。

### 作り手プロフィール `app/u/[username]`
- 投稿数／王道獲得数／実吸評価数／再現回数（段位は将来。プロ認証≠段位）。
